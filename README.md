# ВышКат

Программа хранит транспорт и вещи парка. Все данные вводятся через меню в консоли. После закрытия программы они не сохраняются.

## Запуск

Нужен .NET 10 SDK. 

Из папки, содержащей VyshKat.sln:

```powershell
dotnet restore VyshKat.sln
dotnet build VyshKat.sln
dotnet run --project src/VyshKat/VyshKat.csproj
```

При первом восстановлении нужен доступ к NuGet. Меню позволяет добавить транспорт или вещь, получить количество объектов, полный инвентарь, список транспорта для новичков и суточный расход энергии. В подменю 0 возвращает назад, в основном меню 0 завершает работу.

## Правила

- Простота и качество тормозов — целые числа от 1 до 10; возраст — неотрицательное число полных лет.
- Принятое в реализации правило техосмотра: возраст не более 10 лет и качество тормозов не ниже 5. Эти условия заданы в FleetServiceCenter.
- Новичкам подходит принятый транспорт с простотой не ниже 6.
- Название и номер обязательны; крайние пробелы удаляются. Номер уникален среди транспорта и вещей без учёта регистра. Его вводит пользователь.
- Отказ техосмотра не добавляет транспорт и не резервирует номер. Повтор номера вызывает ошибку операции, после которой меню продолжает работу.
- Энергия измеряется в кВт·ч за сутки, не может быть отрицательной. Обычные велосипеды, самокаты и шлемы не реализуют интерфейс энергопотребления.
- В расходе шкафа и док-станции учитывается их собственное потребление. Энергию, уже учтённую для транспорта, повторно туда не включают.
- Некорректный ввод повторяется; окончание потока ввода завершает программу. Незавершённый объект не добавляется.

## Устройство

| Файл | Ответственность |
| ---  | --- |
| Model.cs | Интерфейсы и модели, проверка допустимости данных |
| Fleet.cs | Коллекции, приёмка через сервис, уникальность номеров, расчёт отчётов |
| Services.cs | Контракт техосмотра и реальные правила проверки |
| ConsoleApplication.cs | Меню, ввод и печать результатов |
| DependencyInjection.cs | Регистрация зависимостей |
| Program.cs | Создание контейнера и запуск приложения |

Transport объединяет состояние родственных видов транспорта. Equipment объединяет вещи. IInventoryItem предоставляет имя и номер обеих иерархий. IEnergyConsumption описывает отдельную возможность и не навязывается всем объектам.

Fleet хранит две коллекции. AllInventory создаёт объединённый список для отчёта; отдельного независимого хранилища инвентаря нет. Снаружи исходные коллекции доступны только для чтения, поэтому нельзя обойти приёмку прямым добавлением.

## SOLID

- **SRP:** модели отвечают за корректность своих значений, сервис — за решение техосмотра, парк — за учёт, ConsoleApplication — за взаимодействие. Расчёт отчёта отделён от его печати.
- **OCP:** расчёт энергии работает через IEnergyConsumption, поэтому новый энергопотребляющий тип учитывается без изменения SumEnergy. Полностью принцип не проводится: новый пункт консольного меню требует изменения switch. Для небольшого приложения это сознательное ограничение, чтобы не вводить сложную систему фабрик.
- **LSP:** каждый наследник Transport может храниться в парке и участвовать в общем отчёте; наследники сохраняют ограничения базового конструктора и доступность общих свойств.
- **ISP:** инвентарный учёт, расход энергии и проверка транспорта разделены на небольшие интерфейсы. Шлему не нужен фиктивный расход энергии.
- **DIP:** Fleet получает IServiceCenter через конструктор и не создаёт FleetServiceCenter самостоятельно. Конкретный сервис регистрируется в DependencyInjection.Configure.

Наиболее явно проявляется DIP: один и тот же парк можно проверить с реальным сервисом и с заменой, заранее возвращающей разрешение или отказ. Microsoft.Extensions.DependencyInjection создаёт приложение и связывает зависимости. Singleton выбран потому, что одна сессия консоли использует один парк. Контейнер доступен только в точке сборки приложения и тестах.

## Пример расширения

Для нового вида электротранспорта достаточно наследника Transport с реализацией IEnergyConsumption. Приёмка, инвентарный отчёт, выбор для новичков и сумма энергии уже работают с ним. В ConsoleApplication нужно добавить выбор и ввод его параметров. Для нового правила техосмотра добавляется другая реализация IServiceCenter и меняется регистрация зависимости. Код Fleet менять не требуется.

## Тесты и покрытие

```powershell
dotnet test VyshKat.sln
dotnet test VyshKat.sln --collect:"XPlat Code Coverage" --results-directory TestResults
```

Тесты проверяют границы характеристик, техосмотр, порог для новичков, суммирование энергии, новый тип вещи, повторные номера между коллекциями, защиту коллекций, подмену зависимости через DI, консольный ввод, ошибки и окончание ввода. StubServiceCenter в тестовом проекте — заглушка, возвращающая заданное значение true или false. Это позволяет независимо проверить реакцию парка на решение сервиса.

ConsoleApplication получает TextReader и TextWriter: приложение использует Console.In/Out, а тесты StringReader/StringWriter. Поэтому ввод можно проверить без ручного набора и изменения глобального Console.

Отчёт coverage.cobertura.xml создаётся в подпапке TestResults. После изменения кода тесты и измерение покрытия нужно повторить. Для просмотра общего покрытия строк в PowerShell:

```powershell
$coverageFile = Get-ChildItem TestResults -Recurse -Filter coverage.cobertura.xml | Sort-Object LastWriteTime -Descending | Select-Object -First 1
[xml]$coverageReport = Get-Content $coverageFile.FullName -Raw
$rate = [double]::Parse($coverageReport.coverage.GetAttribute("line-rate"), [System.Globalization.CultureInfo]::InvariantCulture)
"Покрытие строк: {0:P2}" -f $rate
```


## Ручная демонстрация

1. Добавить самокат с возрастом 0, тормозами 5 и простотой 6 — должен быть принят и показан среди подходящих новичкам.
2. Добавить транспорт возрастом 11 лет — должен быть отклонён.
3. Добавить электросамокат с расходом 2,5 и шкаф с собственным расходом 1 — общий расход 3,5 кВт·ч.
4. Попробовать добавить вещь с уже занятым номером — получить сообщение, число объектов не меняется.
5. Показать количество, инвентарь и список для новичков; завершить работу.
